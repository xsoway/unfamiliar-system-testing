# 分业务类型测试点兜底参考

给不同类型系统做「测试点兜底」，作为 `test-point-dimensions.md` 的补充。**命中你的业务类型时再读对应小节**，当作起点清单，再结合当前系统扩展和裁剪。带 ⭐ 的是该类型最容易翻车的高风险点。

---

## A. 电商 / 商城
- 商品：上下架、库存扣减（超卖/并发）、价格与优惠计算、SKU 组合。
- ⭐ 下单：重复点击下单是否产生重复订单（幂等）。
- ⭐ 支付：支付成功/取消/中断/失败后订单状态流转；支付回调幂等与重试（不会重复扣款/重复发货）。
- 订单：各状态转移（待支付→已支付→已发货→已完成→已取消/已退款）、超时未支付自动取消。
- 购物车：价格变化后再结算、库存不足、分批结算、清空。
- ⭐ 退款/售后：退款金额与路径、部分退款、退库存、异常中断回滚。
- 优惠：优惠券过期/并发领取/叠加规则/使用门槛。
- 物流：运单状态、地址修改（已发货能否改）、多次修改一致性。

## B. 支付 / 账务
- ⭐ 幂等：同一笔交易重复请求、重试，必须返回相同结果且不重复扣款。
- 金额：分/厘精度、大额、负数、0、汇率、多币种。
- ⭐ 一致性：支付状态与账务流水、对账是否一致；超时/中断回调如何对账补齐。
- 渠道：多支付渠道（卡/钱包/桥接）切换、渠道失败降级。
- 撤销/冲正：取消、退款、当日撤销、隔日冲正。
- 安全：签名/验签、防篡改、密钥与回调地址、限额与防刷。
- 边界：余额不足、冻结/解冻、重复退款、退款超原支付金额。

## C. CRM / 企业管理系统
- 客户/线索：创建、去重（同一客户多入口）、分配归属（销售抢单/并发分配）。
- 阶段流转：线索→商机→成交→回款，各阶段状态机与回退权限。
- ⭐ 权限治理：可见性（按角色/数据范围/组织架构）、导出数据权限、越权访问。
- 审批流：多级审批、会签/或签、审批人变更、撤回/驳回再提交。
- 数据：Big 列表/分页/筛选/模糊查询/排序、主数据冗余一致性。
- 导入导出：大批量导入校验、部分失败提示、导出大文件与权限。

## D. 搜索 / 检索
- 查全率/查准率：全部数据满足 vs 部分条件满足 vs 表为空时。
- 模糊/精确/组合条件：多关键字组合、空条件、非法条件、特殊字符转义。
- 分页/排序：超大结果集、边界页码、排序稳定性（同分项顺序）。
- ⭐ 数据变更后一致性：新增/编辑/删除后索引是否及时刷新；脏数据不落库。
- 词典/同义词/近义词（如命中）：通配、全角半角、大小写、停用词。
- 性能：大词频、热词并发、超时降级。

## E. 权限 / 身份认证（IAM）
- 认证：登录成功/失败/锁定/找回密码/多因素/会话过期。
- 授权：角色→权限映射、动态权限（改角色后即时生效）、越权（水平/垂直）。
- ⭐ 会话安全：Token/会话过期、复用、登出后失效、异地登录、并发会话。
- 密码安全：复杂度、历史密码、锁定策略、防爆破/限流。
- 审计：敏感操作留痕、可追溯。

## F. AI / LLM / Agent（概率型，非判断题）
> 传统测试是判断题（Actual == Expected）；Agent 测试是概率题（同一任务跑多次结果可能不同）。
- ⭐ 工具调用：意图→预期工具映射表；故意用不同说法问同一件事，统计工具选择准确率。
- 参数传递：选对工具但参数传错（城市/日期颠倒数）；模糊表述（明天下午/越早越好）能否转成精确参数。
- 缺失信息：用户没给全时是「追问」还是「自己瞎编参数」（会追问的 Agent 更可靠）。
- 循环终止：反复调用/停不下来（token 燃烧）vs 过早放弃；设最大轮次验证超限收场。
- ⭐ 异常处理：工具挂了会不会乱跑、编造结果；「永远查不到」场景是否为了交差编一个答案。
- 幻觉/虚构：答案是否基于真实证据；推理过程是否全程撒谎。
- 上下文：多轮记忆正确性、上下文污染、越权读取。
- 边界约束：目标达成度、异常恢复、边界约束三者都要测。
- 稳定性：同一 prompt 多次运行结果一致性、版本回归对比。

## G. 数据集成 / 迁移 / 报表
- 迁移：数据完整性（条数/字段/关系）、旧数据在新规则下表现、幂等/断点续跑、回滚。
- 集成：多系统数据一致性、事件/消息不丢不重、时序。
- 报表：口径正确性（不同指标定义）、空数据/大表/跨期、导出一致性。

## H. 消息 / 异步 / 定时任务
- 幂等消费：重复消息是否导致重复处理。
- 顺序：乱序消息、依赖前置任务。
- 超时/失败重试：退避、死信、人工补偿。
- 定时触发：时间边界（零点、跨天、跨月）、并发触发、错过窗口补跑。

---

## 使用方式

1. 先判定系统主类型（可能多类型，如「电商 + 支付 + 异步」）。
2. 读对应小节，把 ⭐ 高风险点优先圈出来做测试方向。
3. 叠加 `test-point-dimensions.md` 的通用维度。
4. 结合当前系统真实流程给出**具体可执行**的测试点，勿照搬兜底条目原文。
