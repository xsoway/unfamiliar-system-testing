# 启发式模型、测试预言机与风险矩阵（补充方法论）

在「还不懂系统」时，除了维度清单（`test-point-dimensions.md`）和测试理论（`testing-theory-techniques.md`），这套启发式模型帮你回答两个更基本的问题：**「该往哪些方向想？」** 和 **「我怎么知道一个结果是错的？」**。命中按需使用，不必一次全用。

## 一、测试预言机问题（最容易被忽略的核心）

> 你不理解系统，怎么判断「这看起来不对」？—— 这是陌生系统测试的真正难点，不是「测什么」，而是「凭什么说它错」。

**测试预言机（Test Oracle）= 判断结果是否正确的标准**。没有预言机，测试点再多也找不到 bug。

针对陌生系统的实用预言机（可叠加使用）：

| 预言机 | 怎么用它判断「错」 |
|---|---|
| **已有正确输出** | 另一版本 / 另一实现 / 手工算出的结果，拿来对比 |
| **一致性** | 同样的输入应该得到同样的结果；外部可观察行为未被改变时不应漂移 |
| **已知性 / 合理性** | 结果违反简单常识、world 常识或业务直觉（如金额变负、已删数据还在） |
| **过去经验** | 你在类似系统踩过的坑在这里复现 |
| **内部参考** | 日志、消息、缓存内容能佐证外部结果是否可信 |
| **规范 / 文档** | 需求、接口文档、验收标准里的明确断言 |
| **领域模型** | 虽然不懂实现，但懂业务域（如订单、支付）的一般规则 |

**用法**：每个测试方向先问「我怎么知道这条正确/错误？用哪个预言机？」。没有预言机的断言就是「我觉得它错了」，不可信。

## 二、启发式模型（该往哪些方向想）

### SFDPOT —— 产品元素清单（HTSM 精神）
用「产品由什么组成」来提醒别漏测：

| 元素 | 含义 | 测试方向 |
|---|---|---|
| **S**tructure 结构 | 系统怎么搭的 | 模块、前后端、部署、配置 |
| **F**unction 功能 | 能做什么 | 每个功能的 happy + failure 行为 |
| **D**ata 数据 | 处理哪些数据 | 输入/输出/中间态/持久化 |
| **P**latform 平台 | 跑在什么上面 | 操作系统、浏览器、设备、JDK 等 |
| **O**perations 操作 | 谁怎么用 | 用户操作、运维操作、异常操作 |
| **T**ime 时间 | 时间如何影响 | 并发、超时、定时、跨期、顺序 |

用法：一圈扫下来，看哪些元素你完全没考虑过，就是潜在漏测区。

### FEW HICCUPPS —— 一致性 / 质量预言机（Bolton）
一组「结果应在哪些方面保持一致」的检查角度：
- **F**amiliarity 熟悉性、**E**xplainability 可解释性、**W**orld 世界常识
- **H**istory 历史、**I**mage 图像/表象、**C**omparable 可比对象、**C**laimed 声称行为、**U**ser 用户期望、**P**roduct 产品能力、**P**urpose 意图、**S**tatute 规章
适合做一致性断言：外部结果与内部状态、展示与存储、承诺与实现是否一致。

### Whittaker 攻击模式（How to Break Software）
针对「用户输入 + 代码处理」的攻防清单，陌生系统可用作失败路径激发：非法输入、边界值、组合输入、绕过前端校验、强制错误路径、使依赖失败、压测资源等。本质是把「failure path 怎么找」从空想变成可操作清单。

## 三、风险矩阵（把「哪里损失最大」量化）

最小测试模型的第 8 问是「哪里可能造成最大损失」。把它落成一个 2×2 矩阵，决定**先测谁**：

| 维度 | 打分（1–5） | 判定 |
|---|---|---|
| **影响 Impact** | 坏了的影响多大（用户损失/金额/合规/声誉） | 5=核心交易/资金/敏感数据 |
| **可能性 Likelihood** | 发生概率多高（复杂度/历史缺陷/变更频率） | 5=高复杂度+频繁变更+历史踩坑 |

- **风险值 = 影响 × 可能性** → 排序，优先测最高风险组合。
- 陌生系统初期影响/可能性都难精估：**先给粗分（高/中/低）也不比不给强**，边测边修正。
- 输出：风险表（功能 / 影响分 / 可能性分 / 风险值 / 是否已覆盖），高风险项进「下一步优先实验」。

## 四、探索式测试 charter 模板（把「边学边测」变成可执行会话）

```
Charter（探索任务卡）: 作为 <角色>，我想 <能力目标>，以便 <想学到什么>。
参考：<需求/文档/代码位置（如有）>
时间盒：约 60–90 分钟（超过就停下来记录）
笔记：
  - 我做了什么、观察到什么
  - 数据/状态前后变化
  - 发现了什么未知，需要找谁确认
风险笔记：
  - 这里可能出问题的地方（失败路径）
```

用法：每个探索会话**一个 charter**（一个目标），到时间盒就收尾记录，避免「漫无目的地点」。产出是发现列表 + 新未知 + 下一步，而不是固定用例。

## 五、API / 接口契约检查（陌生后端快速摸底）

当你不懂后端实现时，先把接口当作黑盒按契约验一遍（结合失败路径）：
- 合法输入 → 成功响应、字段与文档一致（结构/类型/错误码）。
- 必填缺失 → 400 且给出字段级错误。
- 非法类型 / 超长 / 越界 → 400 且错误清晰，不返回 500。
- 幂等键重复请求 → 返回相同结果，不重复副作用。
- 下游依赖失败 / 超时 → 返回约定错误码，而非堆栈。

---

## 使用方式

1. 先解决**预言机问题**：每个测试方向先定「用什么判断对错」，否则不测。
2. 用 SFDPOT 扫一遍产品元素，找完全没想到的方向。
3. 用风险矩阵定优先级，把「最大损失处」显式打分。
4. 深入某个方向时，用探索 charter 做一次有边界、有记录的会话。
5. API 场景直接按契约黑盒验。
